NAVRYNT / ARCHITECTURE
MODULAR · API-FIRST · LOCAL-FIRST

Source boundaries designed for teams that expect to extend the product.

NAVRYNT separates domain rules, application use cases, infrastructure adapters and delivery interfaces. The React frontend consumes backend contracts rather than duplicating the domain, while plugin and biometric runtimes sit behind explicit extension boundaries.

Core source layout

The included Python package follows explicit application layering, while the frontend and optional model services stay outside the core domain package.

src/navrynt/
├── domain/            Core domain models, rules and value objects
├── application/       Use cases, ports and application events
├── infrastructure/    Storage, collectors, providers and integrations
├── interfaces/        CLI, REST API and composition/bootstrap surfaces
├── plugins/           Plugin runtime and lifecycle support
├── plugins_sdk/       Plugin developer SDK
├── sdk/               Client/developer SDK components
└── shared/            Config, logging, errors, event bus and utilities

frontend/               React / Vite product frontend
biometric suites/       Isolated face, iris, fingerprint, voice, writer and gait services

Design principles

The product's architectural intent is to preserve replaceable integrations and keep heavy or privileged runtimes from leaking directly into core domain rules.

API FIRST

Thin user interfaces

User-facing interfaces call application/API contracts rather than carrying business rules in the browser.

PLUGIN FIRST

Extension without core rewrites

New collectors and capabilities are intended to be added through plugin/SDK surfaces instead of hard-coding every integration.

LOCAL FIRST

Customer-controlled data

The default product model keeps application data under customer-controlled infrastructure.

BOUNDARIES

Layered dependencies

Domain/application code should not depend directly on web frameworks or concrete persistence implementations.

OPTIONAL RUNTIMES

Heavy ML isolation

Large model dependencies are kept behind extras or isolated services where practical.

AUDITABILITY

Traceable privileged work

Evidence/provenance and privileged actions are designed to remain auditable.

Security boundaries

Self-hosting shifts infrastructure control to the customer, so the product documents explicit operational responsibilities.

Client-side gating is not an authorization boundary. Production deployments should use strong API keys and RBAC mappings, explicit CORS origins, production secrets outside source control, appropriate storage/backups/transport controls, and trusted plugin/model sidecars. External provider, model and dataset rights must be validated for the intended use.
